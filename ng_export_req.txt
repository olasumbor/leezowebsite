
Leezofood Ng.Export — Backend Development &amp; Integration Requirements1. Project OverviewLeezofood Ng.Export is a logistics and procurement website.The frontend has already been developed using HTML, CSS, and JavaScript. The current frontend contains the public website, authentication pages, procurement functionality, procurement history/details, shipment details, request-a-quote functionality, contact page, and user dashboard structure.The current frontend uses localStorage for some functionality because the backend has not yet been connected.The backend should now provide the real database, authentication, user ownership, procurement management, shipment management, and API functionality.Important: The existing frontend design is already established. Backend integration should be done without unnecessarily changing the existing HTML structure, CSS classes, responsive design, or visual appearance.2. Main Backend ResponsibilitiesThe backend should provide:User registration and authenticationSecure login/logout/session managementPassword reset functionalityUser profile/account managementProcurement request managementProcurement historyProcurement detail recordsProcurement status updatesShipment trackingShipment history/detailsRequest-a-quote submission and managementContact/communication form handlingNewsletter subscription handling.Admin functionality for managing users, procurements, shipments and quote requestsSecure authorization so users can only access their own records3. Authentication SystemThe website already has authentication-related frontend files, including:auth.jsdashboard.htmlforgot-password.htmlreset-password.htmlThe backend should implement the actual authentication system.Required functionalityRegistrationUsers should be able to create an account with the required information.The backend should:validate submitted informationcheck whether the email already existssecurely hash passwordscreate the user accountreturn an authenticated session/token where appropriatePasswords must never be stored as plain text.LoginWhen a user signs in:User↓Sign In↓Backend validates credentials↓Successful authentication↓Authenticated session/token↓Dashboard / authorized pagesThe frontend should be able to determine whether the user is authenticated.4. Procurement Access ControlThis is particularly important.The intended behavior is:User clicks "Procurement"        ↓Is user authenticated?        ↓   ┌────┴────┐   │         │  YES        NO   │         │   ↓         ↓Procurement  Sign Inpage         pageIf the user is already signed in, they should be able to access the procurement page directly.If the user is not authenticated, they should be redirected to the sign-in page.However, this must not rely only on frontend JavaScript.The backend must also protect procurement APIs and data.A user should never be able to access another user’s procurement information simply by changing an ID in the URL.For example:procurement-details.html?id=PR1234567890should not automatically mean that anybody can retrieve that procurement.The backend should verify:Authenticated User        ↓Does this procurement belong to this user?        ↓YES → return dataNO  → return unauthorized/forbidden response5. User Ownership of DataEvery procurement, shipment, quote request, etc. that belongs to a user should be associated with that user’s account in the database.For example:Userid: 25name: John Doeemail: john@example.comProcurementid: PR1234567890user_id: 25status: PendingThe backend should use the authenticated user’s ID rather than trusting a user_id supplied by the frontend.This is important for security.6. API Authentication &amp; SecuritySecurity is very important because procurement and shipment information is private user data.The backend should implement:password hashingsecure authenticationauthorizationinput validationserver-side validationprotection against unauthorized record accessrate limiting where appropriatesecure password reset tokensproper CORS configurationprotection against SQL injectionprotection against common API attacksHTTPS in productionappropriate error handlingThe frontend should never be treated as a trusted source of authorization.For example, hiding a procurement page with JavaScript is not sufficient security.The API itself must reject unauthorized requests.24. Frontend/Backend Integration PrincipleThe frontend is already designed and should not be unnecessarily rebuilt.Currently some functionality uses:localStoragehard-coded sample dataJavaScript-generated IDsThese are temporary frontend-development mechanisms.Once the backend is ready, they should be replaced with API calls.For example:CurrentForm↓JavaScript↓localStorage↓Procurement historyFinalForm↓JavaScript↓Backend API↓Database↓Backend response↓FrontendSimilarly:Current procurement detailsURL ID↓Hard-coded JavaScript object↓HTMLFinalURL ID↓Authenticated API request↓Backend/database↓Procurement data↓HTML25. Do Not Trust IDs From the FrontendThe frontend will use IDs in URLs such as:procurement-details.html?id=PR6473092354and potentially:shipment-details.html?id=...These IDs are for identifying the requested record.They are not proof of ownership.The backend must always perform the ownership check.26.
